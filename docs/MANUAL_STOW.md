# 手動の一括収納（PC-42）

## 操作
バックパック管理画面（B、またはバックパックの使用）の右上「一括収納」をクリックする。ポーチ単体・ポーチ設定・ラジアル画面には専用ボタンを追加しない。カーソルにアイテムを持っている間はボタンを無効にする。

通常インベントリ27枠（Inventory index 9〜35）だけを入力にし、開いているバックパック内の装着ポーチへ移す。ホットバー0〜8、防具36〜39、オフハンド40、カーソルは動かさない。元のインベントリ順で処理する。対象バックパックが通常インベントリ内にあっても、その本体や他のバッグを移動しない。

## 判定と残数
- ポーチの既存フィルター（含む/含まない、タグ、個別アイテム、未設定時の挙動）に従う。
- 優先度の大きいポーチから収納。同じ優先度は装着スロットの左から右。空き装着枠は詰めない。
- 自動収納OFFのポーチも手動収納できる。ON/OFFや優先度設定自体は変えない。
- 一つのポーチに入らない残りは次の対応ポーチへ送る。最後に残った分・対象外は元のプレイヤースロットに残す。
- 他のバックパック、単体ポーチ、エンダーチェストには送らない。廃棄・ドロップ・スロット整理もしない。
- 非入れ子対象（バッグ、シュルカーボックス等）は既存制限に従う。名前などのコンポーネントを保持し、同一コンポーネントのスタックだけを結合する。
- 結果はアクションバーに収納した個数（スタック数ではない）を表示。0個なら「収納できるアイテムはありません。」。

## 実装
`BagStowPayload`はcontainerIdだけを送る。新たなキー設定は追加しない。サーバーの`BagMenu.stowAll`が現在のメニューとID、バックパック管理画面、サーバー側、生存、非観戦、空カーソル、バッグ所有・ID一意性を確認する。クライアントは移動元/移動先/個数/アイテムを指定しない。

`BagRouter.routeManual`は、メニューが所有する既存の`rootStorage`を渡され、子ポーチだけを短命ビューとして処理する。開いた親を別ビューで再読込しない。拾得時と共通のpriority安定ソート・残数挿入を使用し、手動経路のみ自動収納ON判定を省く。各収納を親へ保存した後、実際に動いた個数だけ元枠を残数へ置換し、メニュー同期する。旧要求・本体不在/ID重複/死亡・観戦・別画面要求は拒否して何も動かさない。拾得時の「開いた親を対象外にする」ルールは変更しない。

ボタンは既存`SkinnedButton`・自作PNG・ホバー音・アニメーションを再利用する。位置は管理GUI内の(115,2)、55×14。日英4キーは`ModLanguageProvider`で管理し、runDataで生成する。画像・モデル・レシピ・既存payload/操作IDは変更しない。

## 実機確認
1. バックパックへ異なる条件/優先度のポーチを装着する。自動収納OFFのポーチも試す。
2. 通常インベントリとホットバーへ対象素材を分けて置き、一括収納する。通常27枠だけ動くことを確認する。
3. ポーチを満杯近くにし、一部だけ収納されて残りが元枠に残ることを確認する。
4. バッグ本体がホットバー/通常枠/Curios backにある場合、移動後/再オープン/ワールド再起動も確認する。
5. 名前付きアイテム、含まない設定、他バックパック併用、空カーソル/持った状態、連打、実マルチを確認する。

実クライアント描画・操作・ワールド再起動・実マルチは自動GameTestとは別に確認する。
